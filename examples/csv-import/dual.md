1. **不建議直接實作。**以 simplicity 濾鏡看，目前只需 CSV，Factory 預留 JSON、Excel 缺乏需求依據；可先由 Controller → Service → Repository 承接解析與寫入。佇列是否必要，仍需量測 500 筆耗時與請求時限，不能只憑規模決定。

2. **以 reliability 濾鏡看，重試可能覆蓋修正。**舊工作寫入部分資料後中斷，新工作完成修正，舊工作重送便可能覆蓋新值。email 唯一鍵只能避免重複客戶；job_id 也不能判定哪份資料較新。全部寫完、尚未標記 completed 時中斷，同樣會觸發重做。

3. **下一步先定義新舊順序與提交邊界。**確認是否以上傳受理順序為準、是否允許部分成功。若要求整批成功，可將客戶更新與完成狀態放入同一交易；另以資料庫原子版本條件拒絕舊工作覆寫，交易本身不保證新舊順序。驗證中途失敗、提交後重送及新舊工作交錯，再決定執行方式。
